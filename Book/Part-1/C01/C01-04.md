# طراحی غنی از دانش

دانشی که در مدلی مثال `PCB` گنجانده شده است، از «پیدا کردن اسم‌ها» فراتر می‌رود. فعالیت‌ها و قواعد کسب‌وکار درست به همان اندازه موجودیت‌های درگیر در دامنه، مهم هستند؛ هر دامنه‌ای مقوله‌های گوناگونی از مفاهیم خواهد داشت. واکاوی دانش به مدل‌هایی می‌انجامد که بازتاب‌دهنده این نوع بینش هستند. همزمان با تغییرات مدل، توسعه‌دهندگان پیاده‌سازی را `Refactor` می‌کنند تا مدل را بیان کند و استفاده از آن دانش را در اختیار برنامه بگذارد.

دقیقاً زمانی که از موجودیت‌ها و اشیای مقداری فراتر می‌رویم، فرایند واکاوی دانش می‌تواند بسیار پیچیده و فشرده شود، چرا که ممکن است ناسازگاری‌های واقعی میان قواعد کسب‌وکار وجود داشته باشد. `Domain experts` معمولاً آگاه نیستند که فرآیندهای ذهنی‌شان چقدر پیچیده است، زیرا در جریان کار روزمره‌شان، همه این قواعد را مرور می‌کنند، تناقض‌ها را سازش می‌دهند و شکاف‌ها را با تکیه عقل سلیم پر می‌کنند. اما نرم‌افزار نمی‌تواند این کار را بکند. تنها از طریق واکاوی دانش و با همکاری نزدیک با متخصصان نرم‌افزار است که قواعد شفاف‌سازی می‌شوند، جزئیات آن‌ها تکمیل می‌شود، ناسازگاری‌هایشان برطرف می‌گردد یا مشخص می‌شود که اساساً خارج از محدودهٔ مسئله هستند.

## مثال:

### استخراج یک مفهوم پنهان

بیایید با یک `Domain model` بسیار ساده شروع کنیم که می‌تواند مبنای برنامه‌ای برای رزرو کردن بار‌ها (Cargos) برای یک سفر دریایی (Voyage) یک کشتی باشد.

![شکل 1.8](../../../Images/Part-1/C01/1.8.png 'شکل 1.8')
_شکل 1.8_

می‌توانیم بگوییم که مسئولیت برنامه رزرو این است که هر Cargo را به یک Voyage مرتبط سازد و آن رابطه را ثبت و پیگیری کند. تا اینجا خوب است. جایی در کد برنامه ممکن است متدی شبیه این وجود داشته باشد:

```java
public int makeBooking(Cargo cargo, Voyage voyage) {
    int confirmation = orderConfirmationSequence.next();
    voyage.addCargo(cargo, confirmation);
    return confirmation;
}
```
از آنجا که همیشه کنسلی‌های لحظه آخری وجود دارد، رویهٔ استاندارد در صنعت کشتیرانی این است که محموله بیشتری نسبت به آنچه یک کشتی خاص می‌تواند در یک سفر دریایی حمل کند، پذیرفته شود. این کار `Overbooking` (فروش بیش از ظرفیت) نامیده می‌شود. گاهی از درصد ساده‌ای از ظرفیت استفاده می‌شود، مثلاً رزرو ۱۱۰ درصد ظرفیت. در موارد دیگر، قواعد پیچیده‌ای اعمال می‌شود که به مشتریان عمده یا انواع خاصی از بار امتیاز می‌دهد.

این یک استراتژی پایه در دامنه کشتیرانی است که برای هر تاجری در این صنعت شناخته‌شده خواهد بود، اما ممکن است برای تمام افراد فنی یک تیم نرم‌افزاری قابل درک نباشد.

سند نیازمندی‌ها شامل این خط است:

اجازه ۱۰٪ `Overbooking` داده شود.

نمودار کلاس و کد اکنون به این شکل درآمده‌اند:

![شکل 1.9](../../../Images/Part-1/C01/1.8.png 'شکل 1.9')
_شکل 1.9_

```java
public int makeBooking(Cargo cargo, Voyage voyage) {
    double maxBooking = voyage.capacity() * 1.1;
    if ((voyage.bookedCargoSize() + cargo.size()) > maxBooking)
        return –1;
    int confirmation = orderConfirmationSequence.next();
    voyage.addCargo(cargo, confirmation);
    return confirmation;
}
```

اکنون یک قاعده مهم تجاری به‌عنوان یک شرط محافظ درون یک متد کاربردی پنهان شده است. بعدها، در فصل ۴، به اصل `LAYERED ARCHITECTURE` (معماری لایه‌ای) نگاهی خواهیم انداخت که به ما کمک می‌کند تا قاعده `Overbooking` را به یک شیء دامنه منتقل کنیم، اما در حال حاضر بیایید بر این تمرکز کنیم که چگونه می‌توانیم این دانش را صریح‌تر و در دسترس‌تر برای همه در پروژه بسازیم. این کار ما را به راه‌حلی مشابه خواهد رساند.

1.	به شکلی که نوشته شده، بعید است که هیچ `Domain expert` بتواند این کد را برای تأیید قاعده بخواند، حتی با راهنمایی یک توسعه‌دهنده.
2.	برای یک فرد فنیِ غیر تاجر دشوار خواهد بود که متن نیازمندی را به کد ارتباط دهد.

اگر قاعده پیچیده‌تر بود، به همان نسبت بیشتر در خطر می‌بود.

می‌توانیم طراحی را تغییر دهیم تا بهتر این دانش را بدست آوریم. قاعده `Overbooking` یک `Policy` (سیاست) است. سیاست نام دیگری است برای `Design pattern` معروف به `STRATEGY` (Gamma et al. 1995). این الگو معمولاً با نیاز به جایگزینی قواعد و رفتارهای مختلف توجیه می‌شود نیازی که دست‌کم بر اساس دانسته‌های فعلی ما، در اینجا وجود ندارد. اما مفهومی که در تلاش برای مدل‌سازی آن هستیم، درست با معنای یک `Policy` تطابق دارد، که در `DDD` انگیزه‌ای به همان اندازه مهم است. (رجوع کنید به فصل ۱۲)

![شکل 1.10](../../../Images/Part-1/C01/1.8.png 'شکل 1.10')
_شکل 1.10_

کد اکنون به این صورت است:

```java
public int makeBooking(Cargo cargo, Voyage voyage) {
    if (!overbookingPolicy.isAllowed(cargo, voyage))
        return –1;
    int confirmation = orderConfirmationSequence.next();
    voyage.addCargo(cargo, confirmation);
    return confirmation;
}
```

کلاس جدید `Overbooking Policy` شامل این متد است:

```java
public boolean isAllowed(Cargo cargo, Voyage voyage) { 
    return (cargo.size() + voyage.bookedCargoSize()) <=
            (voyage.capacity() * 1.1);
}
```

برای همه روشن خواهد بود که `Overbooking` یک سیاست متمایز است، و پیاده‌سازی آن قاعده صریح و مجزا می‌باشد.

اکنون، من توصیه نمی‌کنم که چنین طراحی مفصلی برای هر جزئی از دامنه اعمال شود. فصل ۱۵، «واکاوی»، به طور عمیق به چگونگی تمرکز بر مهم‌ها و به حداقل رساندن یا جدا کردن هر چیز دیگر می‌پردازد. این مثال برای نشان دادن این منظور است که یک `Domain model` و طراحی متناظر با آن می‌تواند برای تثبیت و به اشتراک‌گذاری دانش به کار رود. طراحی صریح‌تر این مزایا را دارد:

1.	برای رساندن طراحی به این مرحله، برنامه‌نویسان و هر کس دیگری که درگیر است، ماهیت `Overbooking` را به‌عنوان یک قاعده متمایز و مهم کسب‌وکار درک خواهد کرد، نه صرفاً یک محاسبه مبهم.
2.	برنامه‌نویسان می‌توانند خروجی‌های فنی، حتی کد را، به `Domain experts` نشان دهند که باید برای `Domain experts` قابل فهم باشد (با راهنمایی)، و بدین ترتیب حلقه بازخورد را ببندند.
